1. EXECUTIVE SUMMARY & PRODUCT VISION
================================================================================

WHAT IS STRONGTRAK?
-------------------
StrongTrak is a small hardware device installed INLINE in the load path of
gym cable machines - physically bolted between the cable termination and the
weight stack connection. It measures:

  - FORCE: via an inline load cell (strain gauge sensor)
  - MOTION: via an IMU (accelerometer + gyroscope)

Data flows wirelessly via BLE to a phone app, then to a cloud backend for
analysis, tracking, and coaching insights.

THE USER EXPERIENCE VISION
--------------------------
1. User walks up to a cable machine.
2. Scans a QR code mounted on the machine (NOT on the device itself).
3. Phone app opens, identifies which StrongTrak device is on that machine.
4. Device appears to "wake up" and connect instantly.
5. User does their workout. Every rep is captured: force curve, velocity, timing.
6. User walks away. Device goes back to ultra-low-power standby.
7. Data syncs to backend. User sees workout summary on their phone.

CRITICAL DESIGN CONSTRAINTS
---------------------------
- BATTERY LIFE: Must last months to 1+ year on a single battery. The device
  must be "always available" yet draw almost nothing when idle.

- ENVIRONMENT: Installed near a steel weight stack. Subject to vibration,
  shock, EMI (electrical noise from gym equipment motors), RF attenuation
  (radio signals blocked by steel), sweat, dirt, and temperature swings.

- INLINE INSTALLATION: Requires a wrench. Not a casual consumer installation.
  This is a gym owner/operator install or a dedicated hardware install service.

- SCALABILITY: A single gym may have 20-50 StrongTrak devices. The system
  must handle discovery, connection, and data routing without collisions.

2. GLOSSARY OF TERMS
================================================================================

ADC         Analog-to-Digital Converter. Converts analog voltage signals
            (like from a load cell) into digital numbers the microcontroller
            can process.

BLE         Bluetooth Low Energy. A wireless protocol designed for low power
            consumption. Used for communication between device and phone.

Central     In BLE, the device that initiates connections (usually the phone).

Characteristic
            A BLE data container within a Service. Think of it as a single
            variable that can be read, written, or subscribed to for updates.

DFU         Device Firmware Update. The process of updating the firmware on a
            device, often done wirelessly (see FUOTA).

Duty Cycle  The percentage of time something is "on" vs "off." Lower duty
            cycle = lower power consumption.

EMA         Exponential Moving Average. A type of filter that smooths noisy
            data by giving more weight to recent samples.

EMI         Electromagnetic Interference. Electrical noise that can corrupt
            sensor readings or wireless signals.

FUOTA       Firmware Update Over The Air. Updating device firmware via
            wireless connection (BLE or WiFi) without physical access.

GATT        Generic Attribute Profile. The BLE protocol that defines how data
            is organized into Services and Characteristics.

GPIO        General Purpose Input/Output. Pins on a microcontroller that can
            be configured as inputs (read sensors) or outputs (control LEDs).

HX711       A specific IC (integrated circuit) that amplifies tiny signals
            from strain gauge load cells and converts them to digital values.
            Uses bit-banged GPIO protocol. Replaced by NAU7802 in current design.

I2C         Inter-Integrated Circuit. A two-wire communication protocol used
            to connect sensors to microcontrollers. Pronounced "I-squared-C."

IMU         Inertial Measurement Unit. A sensor package containing an
            accelerometer (measures acceleration/tilt) and gyroscope
            (measures rotation rate). Current design uses ICM-20948 9-DOF.

Interrupt   A hardware signal that immediately gets the processor's attention,
            waking it from sleep or interrupting normal code execution.

Load Cell   A transducer (sensor) that converts mechanical force into an
            electrical signal. Strain gauges deform under load, changing
            their resistance.

MCU         Microcontroller Unit. The "brain" of the device - a small

NAU7802     A precision 24-bit ADC with built-in amplifier designed for
            load cell applications. Uses I2C interface at address 0x2A.
            Lower noise and power than HX711, with programmable gain.
            computer on a single chip.

MTU         Maximum Transmission Unit. The largest packet size that can be
            sent in one BLE transaction. Larger MTU = fewer packets needed.

NUS         Nordic UART Service. A pre-defined BLE service that mimics a
            serial port. Simple to use but not optimized for structured data.

Peripheral  In BLE, the device that advertises and accepts connections
            (the StrongTrak sensor). Opposite of Central.

QoS         Quality of Service. Guarantees about data delivery (e.g.,
            "every packet must be acknowledged").

RF          Radio Frequency. The electromagnetic waves used for wireless
            communication (BLE, WiFi, etc.).

RTC         Real-Time Clock. A low-power clock that keeps time even when the
            main processor is asleep.

Service     A BLE container that groups related Characteristics. Like a
            folder containing files.

SPI         Serial Peripheral Interface. A faster alternative to I2C for
            connecting sensors, using 4 wires instead of 2.

State Machine
            A programming pattern where the system is always in one defined
            "state" and transitions between states based on events. Much
            cleaner than complex if/else chains.

Strain Gauge
            A resistor that changes resistance when stretched or compressed.
            The sensing element inside a load cell.

UUID        Universally Unique Identifier. A 128-bit number that identifies
            a BLE Service or Characteristic. Custom services need custom UUIDs.

ZUPT        Zero Velocity Update. A technique to reduce drift in position
            tracking by resetting velocity to zero when the device is known
            to be stationary.

THE BIG PICTURE
---------------
StrongTrak is a distributed system with four major components:

  ┌─────────────────┐      BLE       ┌─────────────────┐
  │   STRONGTRAK    │◄──────────────►│   PHONE APP     │
  │     DEVICE      │                │   (Central)     │
  │   (Peripheral)  │                └────────┬────────┘
  └─────────────────┘                         │
                                              │ HTTPS/WebSocket
                                              ▼
                                    ┌─────────────────┐
                                    │     BACKEND     │
                                    │   (Cloud API)   │
                                    └────────┬────────┘
                                              │
                                              ▼
                                    ┌─────────────────┐
                                    │    DATABASE     │
                                    │  (User Data,    │
                                    │   Workouts)     │
                                    └─────────────────┘

Later, we add a fifth component for multi-device scaling:

  ┌─────────────────┐      BLE       ┌─────────────────┐
  │   STRONGTRAK    │◄──────────────►│   GYM HUB       │
  │    DEVICES      │                │   (Gateway)     │
  │   (Multiple)    │                └────────┬────────┘
  └─────────────────┘                         │
                                              │ WiFi/Ethernet
                                              ▼
                                    ┌─────────────────┐
                                    │     BACKEND     │
                                    └─────────────────┘

DATA OWNERSHIP MODEL
--------------------
- The DEVICE knows nothing about users. It has a unique device_id burned in.
- The BACKEND maps device_id -> machine_id -> gym_id.
- When a user scans a QR code, the app asks the backend: "What device_id is
  associated with this machine?" Then it connects to that device via BLE.
- The backend associates workout data with the user based on:
  * Which user's app connected to which device_id
  * Time window of the session

This means the device firmware stays simple and doesn't need user management.

KEY HARDWARE INTERFACES
-----------------------
1. NAU7802 <-> MCU: I2C interface at address 0x2A. Provides 24-bit ADC readings
   with programmable gain (1x to 128x). Sample rates up to 320 SPS with built-in
   digital filtering. Much lower power and noise compared to HX711.

2. IMU <-> MCU: I2C bus at 400 kHz. The ICM-20948 provides 9-DOF sensing with
   accelerometer, gyroscope, and magnetometer. Can generate interrupts on motion
   detection, which is critical for waking the device from sleep.

3. BLE Radio: Built into the nRF52840. Shares the same processor but has its
   own power domain that can stay active during sleep.

4. I2C Bus Sharing: Both NAU7802 and IMU share the same I2C bus. Careful timing
   and addressing prevents conflicts. NAU7802 uses address 0x2A, IMU uses 0x68.

================================================================================

The firmware should be organized into clean, single-responsibility modules.
Here's the target structure:

strongtrak/
├── platformio.ini              # Build configuration
├── src/
│   ├── main.cpp                # Entry point, setup(), loop() orchestration
│   │
│   ├── config.h                # Global constants, pin definitions, timing
│   │
│   ├── state_machine.h/.cpp    # Central state machine (IDLE, CONNECTED, etc.)
│   │
│   ├── sensors/
│   │   ├── imu.h/.cpp          # IMU abstraction (ICM-20948 + variants)
│   │   ├── loadcell.h/.cpp     # NAU7802 + load cell driver
│   │   └── battery.h/.cpp      # Battery voltage monitoring
│   │
│   ├── processing/
│   │   ├── filter.h/.cpp       # EMA, Kalman, or other filters
│   │   ├── rep_detector.h/.cpp # Rep detection algorithm (Phase 4)
│   │   └── calibration.h/.cpp  # Load cell calibration routines
│   │
│   ├── comms/
│   │   ├── ble_service.h/.cpp  # BLE GATT service definitions
│   │   ├── ble_streaming.h/.cpp# Data packet formatting & transmission
│   │   └── protocol.h          # Packet structure definitions
│   │
│   ├── power/
│   │   ├── power_manager.h/.cpp# Sleep modes, wake sources
│   │   └── advertising.h/.cpp  # Advertising interval management
│   │
│   └── storage/
│       └── flash_log.h/.cpp    # Unclaimed rep storage (Phase 4+)
│
├── include/                    # Public headers if needed
├── lib/                        # Private/local libraries
├── test/                       # Unit tests (native platform)
└── tools/                      # Helper scripts

MODULE RESPONSIBILITIES
-----------------------

main.cpp
  - Initialize all modules in correct order
  - Run the main loop (non-blocking)
  - Delegate to state_machine for decision-making

state_machine
  - Defines all system states (IDLE_ADV_SLOW, CONNECTED, STREAMING, etc.)
  - Handles transitions based on events (connection, motion, timeout)
  - Coordinates power management decisions

sensors/imu
  - Initialize IMU with correct variant detection (current code)
  - Configure motion interrupts for wake
  - Read filtered accelerometer/gyroscope data
  - Provide "is moving" detection

sensors/loadcell
  - Initialize NAU7802 with gain setting and sample rate
  - Read raw 24-bit ADC values via I2C
  - Apply calibration (offset + scale factor)
  - Return force in kg or Newtons
  - Handle I2C timing to avoid bus conflicts with IMU

sensors/battery
  - Read battery voltage via ADC
  - Provide battery percentage estimate
  - Alert when low

processing/filter
  - Generic filtering (EMA, moving average, Kalman)
  - Configurable per-signal

processing/rep_detector
  - State machine for rep detection (later phase)
  - Detects: rep start, rep end, concentric/eccentric phases
  - Outputs: rep count, peak force, tempo

processing/calibration
  - Store calibration values in flash
  - Provide calibration routines (tare, two-point cal)

comms/ble_service
  - Define custom GATT service with characteristics
  - Handle connection/disconnection callbacks
  - Manage MTU negotiation

comms/ble_streaming
  - Pack sensor data into efficient packets
  - Handle flow control (don't overflow buffers)
  - Provide send queue with retry logic

power/power_manager
  - Configure sleep modes (System ON, System OFF)
  - Manage wake sources (BLE, GPIO, RTC timer)
  - Coordinate with state machine

power/advertising
  - Set advertising intervals based on state
  - Manage advertising data (device name, service UUIDs)

6. BLE SERVICES & CHARACTERISTICS STRATEGY
================================================================================

PHASE 1-2: USE NORDIC UART SERVICE (NUS)
-----------------------------------------
For early development, continue using NUS. It's simple and works.

  Service: Nordic UART Service (6E400001-B5A3-F393-E0A9-E50E24DCCA9E)
  Characteristics:
    - TX (notify): Device sends data to phone
    - RX (write):  Phone sends commands to device

Data format: ASCII strings like "F:123.4,A:0.12,0.03,9.81\n"

Pros: Simple, works with generic BLE UART apps, easy debugging.
Cons: Inefficient (text vs binary), no structured data, limited features.

PHASE 3+: MIGRATE TO CUSTOM GATT SERVICE
----------------------------------------
Define a custom service tailored to StrongTrak's needs:

  Service: StrongTrak Sensor Service (custom 128-bit UUID)

  Characteristics:

  1. Force Data (notify, 4 bytes)
     - Raw or calibrated force as float32
     - Notify rate: 10-80 Hz

  2. IMU Data (notify, 12 bytes)
     - Accel X,Y,Z as int16 (scaled)
     - Or full 24 bytes for accel + gyro

  3. Rep Event (notify, variable)
     - Triggered on rep completion
     - Contains: rep number, peak force, duration, tempo

  4. Device Status (read, 8 bytes)
     - Battery level, connection state, error flags

  5. Command (write, variable)
     - Tare, calibrate, start/stop streaming, enter DFU

  6. Config (read/write, variable)
     - Sampling rate, filter settings, thresholds

WHY CUSTOM SERVICE LATER?
-------------------------
- Binary data is 3-5x more efficient than ASCII text
- Separate characteristics allow subscribing to only what you need
- Structured data reduces parsing errors
- Enables future features (config, commands) cleanly

BUT: Custom services require custom app code. NUS works with off-the-shelf
apps. Start simple, migrate when you have app development resources.

6.1 BLE DATA CONTRACT (CURRENT IMPLEMENTATION)
------------------------------------------------------------------------------

This section defines the AUTHORITATIVE data format exchanged between firmware
and client applications. Both sides MUST implement this contract exactly.

CURRENT FORMAT: ASCII CSV over Nordic UART Service (NUS)
--------------------------------------------------------

Service UUID: 6E400001-B5A3-F393-E0A9-E50E24DCCA9E
TX Characteristic: 6E400003-B5A3-F393-E0A9-E50E24DCCA9E (notify)
RX Characteristic: 6E400002-B5A3-F393-E0A9-E50E24DCCA9E (write)

STREAMING DATA FORMAT (TX):
  "height_cm,velocity_m_s,weight_lbs\n"

  Field 1: height_cm     - Vertical position in cm from tare point (float, 1 decimal)
  Field 2: velocity_m_s  - Vertical velocity in m/s (float, 2 decimals)
  Field 3: weight_lbs    - Load cell reading in pounds (float, 2 decimals)

  Example: "12.5,0.34,45.67\n"
  
  Transmission rate: 10 Hz (100ms intervals)
  Encoding: ASCII UTF-8, newline-terminated
  Parser: Bluetooth_Dashboard/src/lib/parser.ts

COMMAND FORMAT (RX):
  Commands are ASCII strings, newline-terminated:
  
  | Command        | Description                              | Response          |
  |----------------|------------------------------------------|-------------------|
  | tare           | Zero position and load cell              | OK: tared         |
  | cal <lbs>      | Calibrate with known weight in lbs       | OK: calibrated... |
  | status         | Get device status                        | Multi-line status |
  | help           | List available commands                  | Commands: ...     |

  Example: "cal 5\n" → Calibrate with 5 lb weight

STATUS RESPONSE FORMAT:
  Multi-line ASCII with key-value pairs:
  === Status ===
  loadcell_raw: <int32>
  zero_offset: <int32>
  cal_factor: <float>
  backend: NAU7802
  weight_lbs: <float>
  imu_ok: 1
  mag_present: 1

DATA LOSS DETECTION:
  - Currently: Timestamp comparison on client side (parser.ts uses Date.now())
  - Gaps >150ms between packets may indicate loss
  - Future: Add sequence number to binary format when migrating

ENDIANNESS & ENCODING NOTES (for future binary format):
  - All multi-byte integers: Little-endian (native ARM Cortex-M4)
  - Float32: IEEE 754, little-endian
  - Signed integers: Two's complement
  - Strings: UTF-8, null-terminated or length-prefixed

FUTURE BINARY FORMAT (Phase 3+):
  When migrating to custom GATT service, use this binary structure:
  
  | Offset | Size | Type    | Field        | Units/Scale            |
  |--------|------|---------|--------------|------------------------|
  | 0      | 4    | uint32  | timestamp_ms | ms since boot          |
  | 4      | 2    | int16   | height_mm    | 0.1mm per LSB          |
  | 6      | 2    | int16   | velocity     | 0.01 m/s per LSB       |
  | 8      | 2    | int16   | weight       | 0.01 lbs per LSB       |
  | 10     | 2    | int16   | accel_x      | 0.001 g per LSB        |
  | 12     | 2    | int16   | accel_y      | 0.001 g per LSB        |
  | 14     | 2    | int16   | accel_z      | 0.001 g per LSB        |
  | 16     | 2    | int16   | gyro_x       | 0.1 deg/s per LSB      |
  | 18     | 2    | int16   | gyro_y       | 0.1 deg/s per LSB      |
  | 20     | 2    | int16   | gyro_z       | 0.1 deg/s per LSB      |
  | 22     | 1    | uint8   | sequence     | Packet sequence 0-255  |
  | 23     | 1    | uint8   | flags        | Status/error bits      |
  |--------|------|---------|--------------|------------------------|
  | Total  | 24 bytes                                               |
  
  Scale factor rationale:
  - int16 weight at 0.01 lbs/LSB: Range ±327 lbs, resolution 0.01 lbs
  - int16 height at 0.1mm/LSB: Range ±3.2m, resolution 0.1mm  
  - int16 velocity at 0.01 m/s/LSB: Range ±3.27 m/s, resolution 1 cm/s

9. QR CLAIM FLOW & BLE DISCOVERY
================================================================================

This is how the "scan and it wakes" illusion works:

USER FLOW
---------
1. User opens StrongTrak app
2. App shows "Scan a machine to start"
3. User scans QR code on machine
4. QR contains: machine_id (e.g., "gym123-cable-crossover-1")
5. App calls backend: GET /api/machines/{machine_id}/device
6. Backend returns: { "device_id": "ST-00A1B2C3", "device_name": "StrongTrak-A1B2" }
7. App starts BLE scan, filtering for device_name or device_id in advertising data
8. Device is found (was advertising all along at low duty cycle)
9. App connects
10. Connection triggers device to exit low-power mode and start streaming

THE "INSTANT WAKE" ILLUSION
---------------------------
The device isn't actually asleep. It's advertising continuously, just slowly
(e.g., one advertisement every 3 seconds). The trick:

- The QR scan -> backend lookup takes 0.5-2 seconds (network latency)
- BLE scan can start during this time
- By the time the UI says "connecting," the device was likely already found
- The "wake" is just the UI transition, not the device transition

If the device truly needs to wake faster:
- IMU motion interrupt can trigger faster advertising
- When someone touches the cable, device detects motion -> boosts to 100ms ads
- This increases discoverability just when someone is about to use it

ADVERTISING DATA STRATEGY
-------------------------
The device should advertise:
- Device name: "StrongTrak-XXXX" (last 4 of device_id)
- Service UUID: StrongTrak custom service (or NUS early on)
- Manufacturer data: Full device_id for exact matching

This allows the app to:
- Filter scan results by service UUID (fast)
- Match exact device_id from backend response
- Connect to the correct device even with 50 devices in range

11. POWER STATE MACHINE
================================================================================

The device should operate as a state machine with well-defined power modes:

                    ┌──────────────────────────────────────────┐
                    │                                          │
         boot       ▼                                          │
      ──────► ┌───────────┐  motion detected   ┌───────────┐   │
              │   IDLE    │───────────────────►│  BOOST    │   │
              │ ADV_SLOW  │◄───────────────────│ ADV_FAST  │   │
              └─────┬─────┘   timeout (10s)    └─────┬─────┘   │
                    │                                │         │
                    │ BLE connect                    │ BLE connect
                    │                                │         │
                    ▼                                ▼         │
              ┌─────────────────────────────────────────┐      │
              │              CONNECTED                  │      │
              │  (low-power idle, waiting for command)  │      │
              └──────────────────┬──────────────────────┘      │
                                 │                             │
                                 │ start streaming command     │
                                 ▼                             │
              ┌─────────────────────────────────────────┐      │
              │              STREAMING                  │      │
              │  (active sampling + BLE transmission)   │      │
              └──────────────────┬──────────────────────┘      │
                                 │                             │
                                 │ stop command / idle timeout │
                                 │                             │
                    ┌────────────┴────────────┐               │
                    │                         │               │
                    ▼                         ▼               │
              ┌───────────┐            ┌───────────┐          │
              │ CONNECTED │            │ DISCONNECT│──────────┘
              │  (idle)   │            │ ADV_SLOW  │
              └───────────┘            └───────────┘


STATE DEFINITIONS
-----------------

IDLE_ADV_SLOW (Target: <15µA average)
  - Advertising every 3000ms (3 seconds)
  - TX power: -8 dBm (low, saves power)
  - MCU in System ON sleep between advertisements
  - IMU in low-power mode with motion interrupt enabled
  - NAU7802 powered down (AVDDS=0 via I2C register)
  - Wake sources: BLE connection, IMU motion interrupt

BOOST_ADV_FAST (Target: <200µA average)
  - Triggered by IMU motion interrupt
  - Advertising every 100ms for 10 seconds
  - TX power: 0 dBm (higher for better discoverability)
  - After 10 seconds without connection, return to IDLE_ADV_SLOW
  - Purpose: When someone touches the cable, device becomes highly discoverable

CONNECTED (Target: <100µA average)
  - BLE connection established
  - Advertising stopped
  - Waiting for commands from Central
  - IMU in low-power mode (or off)
  - NAU7802 powered down
  - MCU mostly sleeping, wakes on BLE events

STREAMING (Target: <5mA average)
  - Active data collection and transmission
  - IMU sampling at 20 Hz (current config, adjustable)
  - NAU7802 sampling at 5 Hz (force curve capture)
  - BLE notifications at configured rate
  - MCU mostly active

ERROR (Varies)
  - Something went wrong (sensor failure, BLE error)
  - LED blinking pattern indicates error type
  - May attempt recovery or wait for reset

DFU_READY (Full power)
  - Bootloader mode, ready for firmware update
  - Triggered by command or button combo
  - Full power, waiting for DFU transfer

12. ADVERTISING STRATEGY & POWER TRADEOFFS
================================================================================

THE FUNDAMENTAL TRADEOFF
------------------------
Advertising more frequently = more discoverable = higher power consumption.
Advertising less frequently = harder to find = lower power consumption.

ADVERTISING INTERVALS EXPLAINED
-------------------------------
When a BLE Peripheral advertises, it sends a packet on 3 channels:
  - Channel 37 (2402 MHz)
  - Channel 38 (2426 MHz)
  - Channel 39 (2480 MHz)

Each advertisement takes ~1-3ms of radio time. The interval between
advertisements determines average power consumption.

INTERVAL MATH
-------------
Rough power consumption (nRF52840, 0 dBm TX):
  - 100ms interval:  ~100µA average
  - 500ms interval:  ~20µA average
  - 1000ms interval: ~10µA average
  - 3000ms interval: ~4µA average

DISCOVERY TIME
--------------
A Central (phone) scanning for devices will find an advertising device
when their windows overlap. Typical phone scan:
  - Scan window: 30-50ms
  - Scan interval: 100-200ms (iOS) or configurable (Android)

With 3-second advertising interval, worst-case discovery time:
  - 3 seconds to next advertisement
  - Plus scan/advertisement alignment
  - Total: up to 3-4 seconds

With 100ms advertising interval:
  - Typically found within 100-300ms

THE "INSTANT" ILLUSION STRATEGY
-------------------------------
We want the user to feel like scanning the QR code "wakes" the device
instantly. Here's how to create that illusion:

1. PIPELINE THE DELAY:
   - QR scan triggers network request to backend
   - Backend lookup takes 0.5-2 seconds
   - BLE scan starts immediately in parallel
   - By the time backend responds, device may already be found

2. USE MOTION BOOST:
   - When someone touches the cable machine (adjusts weight, grabs handle),
     the IMU detects motion
   - Device immediately boosts to 100ms advertising for 10 seconds
   - By the time user scans QR, device is in fast-advertising mode

3. UI TIMING TRICKS:
   - Show "Connecting..." animation for minimum 1 second regardless
   - Gives time for discovery even with slow advertising
   - Users expect a brief connection delay

4. SCAN RESULT CACHING:
   - App can cache known devices it's seen recently
   - If device was seen in last 5 minutes, skip full scan

RECOMMENDED ADVERTISING PARAMETERS
----------------------------------
Idle State (IDLE_ADV_SLOW):
  - Interval: 3000ms (±50ms random jitter)
  - TX Power: -8 dBm (range ~10m indoors)
  - Duration: Indefinite

Motion-Boosted State (BOOST_ADV_FAST):
  - Interval: 100ms
  - TX Power: 0 dBm (range ~20m indoors)
  - Duration: 10 seconds, then return to idle

Connected State:
  - Connection interval: 15-30ms (per Apple guidelines)
  - Slave latency: 0 during streaming, up to 4 when idle
  - Supervision timeout: 4 seconds

14. TOP TECHNICAL RISKS & MITIGATIONS
================================================================================

RISK 1: LOAD CELL ELECTRICAL NOISE
----------------------------------
Severity: MEDIUM (reduced from HIGH due to NAU7802's superior noise rejection)
Description: The NAU7802 amplifies tiny signals (microvolts) from the load cell.
  Electrical noise from gym equipment, LED lights, or the MCU can affect readings.
  Note: NAU7802 has much better noise performance than HX711 due to its 24-bit
  ADC and built-in digital filtering.

Symptoms:
  - Noisy force readings
  - Drift over time
  - Jumps or spikes in data

Mitigations:
  - Use shielded cable for load cell connection
  - Keep NAU7802 wires short (<10cm if possible)
  - NAU7802 has internal filtering; configure sample rate appropriately
  - Software filtering (EMA or median filter) for additional smoothing
  - Sample multiple times and average if needed

Test: Read force with no load for 1 minute. Noise should be <0.1 kg peak-to-peak.

RISK 2: RF SHADOWING FROM STEEL WEIGHT STACK
--------------------------------------------
Severity: HIGH
Description: The steel weight stack acts as a radio shield. If the device
  antenna is behind the stack (from phone's perspective), signal may be blocked.

Symptoms:
  - Weak or no BLE connection
  - High packet loss
  - Works in lab, fails in gym

Mitigations:
  - Mount device where antenna has clear path (not blocked by steel)
  - Use external antenna routed to better position
  - Test in actual gym during installation
  - Increase TX power if needed (costs battery)
  - Consider device orientation requirements

Test: Place device behind steel plate, measure signal strength vs. open air.

RISK 3: BATTERY LIFE NOT MEETING TARGETS
----------------------------------------
Severity: HIGH
Description: If idle current is too high, battery dies in weeks instead of months.

Symptoms:
  - Device dead when user returns
  - Frequent battery replacements needed

Mitigations:
  - Measure current in each state with proper equipment
  - Use Nordic Power Profiler Kit II
  - Identify and eliminate current hogs
  - Ensure all unused peripherals are disabled
  - Verify pull-up/pull-down resistor configurations
  - Test with actual target battery

Test: Measure idle current. Target: <15µA. If higher, profile and fix.

RISK 4: BLE CONNECTION LATENCY IN CROWDED RF ENVIRONMENT
---------------------------------------------------------
Severity: MEDIUM
Description: In a gym with many devices (phones, smartwatches, other StrongTrak
  units), BLE discovery and connection may be slow or unreliable.

Symptoms:
  - Long time to connect
  - Connection drops frequently
  - Works at home, struggles at gym

Mitigations:
  - Use unique device names/IDs for filtering
  - Implement reconnection logic
  - Use faster advertising on motion
  - Test in actual gym environment
  - Consider dedicated advertising channels

Test: Place 5+ BLE devices in room, verify can still connect in <5 seconds.

RISK 5: LOAD CELL CALIBRATION DRIFT
-----------------------------------
Severity: MEDIUM
Description: Load cells can drift with temperature, mechanical settling, or
  fatigue. Calibration done at install may not hold over time.

Symptoms:
  - Force readings incorrect after days/weeks
  - Zero offset drifts
  - Scale factor changes

Mitigations:
  - Use high-quality load cell rated for application
  - Implement easy re-tare (user can zero via app)
  - Store calibration with temperature compensation if needed
  - Periodic recalibration recommendation in app

Test: Calibrate, wait 1 week, verify still accurate with known weight.

RISK 6: INSTALLATION SAFETY / LOAD PATH INTEGRITY
-------------------------------------------------
Severity: HIGH (SAFETY!)
Description: The device is in the load path. If it fails mechanically, weight
  could drop, causing injury.

Symptoms:
  - Mechanical failure under load
  - Connector loosening over time
  - Cable abrasion at connection point

Mitigations:
  - Over-engineer mechanical connection (use rated hardware)
  - Use safety factor of 5x+ on all load-bearing components
  - Professional installation only (not user-installed)
  - Regular inspection protocol
  - Consider fail-safe design (if device fails, weight stays attached)
  - Liability/insurance considerations

Test: Load test to 3x rated capacity. Fatigue test with 10,000 cycles.

RISK 7: IMU POSITION TRACKING DRIFT
-----------------------------------
Severity: LOW (if used correctly)
Description: Double-integrating accelerometer data accumulates error quickly.
  Position estimate drifts unbounded without external reference.

Symptoms:
  - Position says 10 meters when device moved 1 meter
  - Drift accelerates over time

Mitigations:
  - Only use for short-term / relative measurements
  - Implement ZUPT (Zero Velocity Update) when stationary
  - Reset/tare frequently
  - Use for gesture detection, not absolute position
  - Consider: is position tracking actually needed for StrongTrak?

Assessment: For rep detection, you likely need force + motion detection, not
  absolute position. The IMU is useful for direction/velocity during rep,
  not tracking where the device is in space.


================================================================================
15. BEST PRACTICES FOR NOVICE EMBEDDED DEVELOPMENT
================================================================================

CODE ORGANIZATION
-----------------
1. ONE RESPONSIBILITY PER FILE
   Each .h/.cpp pair should do ONE thing. If a file is doing multiple things,
   split it. Examples:
   - loadcell.h: Only load cell operations
   - ble_streaming.h: Only BLE data transmission
   
2. PREFER NAMESPACES OVER CLASSES (for simple modules)
   You're doing this already (imu::, teleplot::). It's simpler than classes
   when you don't need multiple instances.
   
3. AVOID GLOBAL STATE where possible
   If you need globals, put them in an anonymous namespace in the .cpp file
   (static linkage) and expose via getter functions.

4. USE const AND constexpr LIBERALLY
   If a value doesn't change, mark it const. If it's known at compile time,
   use constexpr. This catches bugs and enables optimization.

   // Bad
   int sampleRate = 50;
   
   // Good
   static constexpr int kSampleRate = 50;

NAMING CONVENTIONS
------------------
1. FILES: lowercase_with_underscores.cpp
   (or lowercase.cpp - pick one and be consistent)

2. NAMESPACES: lowercase (e.g., imu::, teleplot::)

3. FUNCTIONS: camelCase or lowercase_with_underscores (pick one!)
   e.g., imu::begin(), loadcell::readForce()

4. CONSTANTS: kPascalCase or ALL_CAPS
   e.g., kSampleIntervalMs, MAX_BUFFER_SIZE

5. TYPES/STRUCTS: PascalCase
   e.g., SmoothingConfig, Reading

6. MEMBER VARIABLES: m_camelCase or trailing_underscore_
   e.g., m_calibrationOffset or calibration_offset_

7. LOCAL VARIABLES: camelCase
   e.g., currentForce, elapsedMs

PICK A STYLE AND STICK TO IT. Consistency matters more than which style.

STATE MACHINES
--------------
Use explicit state machines instead of complex boolean flags.

// Bad
bool isConnected;
bool isStreaming;
bool isCalibrating;
bool isMotionDetected;
// ... 16 possible combinations, most invalid

// Good
enum class State {
  IDLE_ADV_SLOW,
  BOOST_ADV_FAST,
  CONNECTED,
  STREAMING,
  CALIBRATING,
  ERROR
};
State currentState = State::IDLE_ADV_SLOW;

Transition between states in one place (a switch statement or state table).

AVOID BLOCKING DELAYS
---------------------
Never use delay() in loop() for anything but debugging.
Use millis() and non-blocking patterns.

// Bad (blocks everything)
void loop() {
  readSensor();
  delay(20);  // Nothing else can happen for 20ms!
}

// Good (non-blocking)
void loop() {
  uint32_t now = millis();
  if (now - lastSampleMs >= 20) {
    lastSampleMs = now;
    readSensor();
  }
  // Other things can happen here
}

LOGGING WITHOUT DESTROYING BATTERY
----------------------------------
Serial output costs power and time. In production, minimize logging.

// Development: verbose logging
#define DEBUG_LOG 1

#if DEBUG_LOG
  #define LOG(msg) Serial.println(msg)
#else
  #define LOG(msg) ((void)0)  // Compiles to nothing
#endif

Or use log levels:
enum LogLevel { NONE, ERROR, WARN, INFO, DEBUG };
void log(LogLevel level, const char* msg);

In production, set level to ERROR or NONE.

WHAT NOT TO DO
--------------
1. DON'T USE String CLASS for anything performance-critical
   Arduino String causes heap fragmentation. Use char[] and snprintf().
   
   // Bad
   String message = "Force: " + String(force) + " kg";
   
   // Good
   char buffer[32];
   snprintf(buffer, sizeof(buffer), "Force: %.2f kg", force);

2. DON'T ALLOCATE MEMORY DYNAMICALLY after setup()
   malloc/new in loop() will eventually fragment memory and crash.
   Pre-allocate buffers at compile time or in setup().

3. DON'T IGNORE RETURN VALUES
   If a function returns bool for success/failure, CHECK IT.

   // Bad
   ble::init();  // Ignoring return value
   
   // Good
   if (!ble::init()) {
     enterErrorState();
   }

4. DON'T BLOCK IN CALLBACKS
   BLE event callbacks must return quickly. Don't do heavy processing there.
   Set a flag and handle in loop().

5. DON'T TRUST FLOATING POINT EQUALITY
   
   // Bad
   if (force == 0.0f) { ... }
   
   // Good
   if (fabs(force) < 0.001f) { ... }

6. DON'T FORGET TO HANDLE WRAPAROUND
   millis() wraps around every ~49 days. Use subtraction, not comparison.
   
   // Bad (breaks at wraparound)
   if (millis() > lastTime + interval) { ... }
   
   // Good (always works)
   if (millis() - lastTime >= interval) { ... }

TESTABILITY
-----------
1. PURE FUNCTIONS when possible
   A function that takes inputs and returns outputs without side effects is
   easy to test.

   // Easy to test
   float applyEMA(float current, float previous, float alpha);
   
   // Hard to test (depends on hardware)
   float readLoadCell();

2. DEPENDENCY INJECTION (simple version)
   Pass interfaces to functions instead of hardcoding hardware calls.
   
   // Hard to test
   void processForce() {
     float f = loadcell::read();  // Hardcoded to real hardware
     ...
   }
   
   // Easier to test
   void processForce(float rawForce) {  // Pass the value in
     ...
   }

3. NATIVE UNIT TESTS
   PlatformIO supports [env:native] for running tests on your PC.
   Test algorithms without needing hardware.

19. REP DETECTION DESIGN SPECIFICATION
================================================================================

This section provides detailed design guidance for implementing rep detection.

------------------------------------------------------------------------------
19.1 ALGORITHM OVERVIEW
------------------------------------------------------------------------------

The rep detection algorithm uses FORCE as the primary trigger, with optional
IMU data for phase detection and validation.

RATIONALE FOR FORCE-BASED DETECTION:
- Force directly correlates to weight movement (cable under tension = work)
- IMU can be noisy during exercise (vibration, user movement)
- Force thresholds are more stable and predictable than acceleration
- IMU data enhances phase detection but is not required for basic counting

STATE MACHINE:
  ┌─────────────┐      force > START_THRESHOLD      ┌─────────────┐
  │    IDLE     │ ────────────────────────────────► │   IN_REP    │
  │             │ ◄──────────────────────────────── │             │
  └─────────────┘      force < END_THRESHOLD        └─────────────┘
                       AND duration > MIN_DURATION

------------------------------------------------------------------------------
19.2 THRESHOLD VALUES AND TUNING
------------------------------------------------------------------------------

Initial recommended values (TUNE WITH TESTING):

  START_THRESHOLD:  2.0 lbs above baseline noise
    - Rationale: Most cable exercises involve >5 lb cable tension
    - Too low: False triggers from cable adjustment, bumps
    - Too high: Misses light weight exercises
    
  END_THRESHOLD:    0.5 lbs above baseline (near zero)
    - Rationale: Rep ends when weight is released/returned
    - Should be lower than START to provide hysteresis
    
  MIN_REP_DURATION: 400 ms (0.4 seconds)
    - Rationale: Fastest realistic rep is ~0.5 seconds
    - Filters out bumps, adjustments, accidental triggers
    
  MAX_REP_DURATION: 10000 ms (10 seconds)  
    - Rationale: If rep exceeds this, likely stuck or error
    - Auto-reset state machine to IDLE
    
  SETTLING_TIME:    500 ms between reps
    - Rationale: Prevents double-counting on bouncy movements
    - Time after rep ends before new rep can start

NOISE FLOOR CALIBRATION:
  - After tare, sample force for 1-2 seconds
  - Calculate standard deviation of readings
  - Set START_THRESHOLD = 3 * stddev + baseline
  - This adapts to sensor noise level automatically

------------------------------------------------------------------------------
19.3 METRIC DEFINITIONS
------------------------------------------------------------------------------

REP METRICS (calculated per rep):

  rep_number:    Sequential count since session start (1, 2, 3, ...)
  
  peak_force:    Maximum force reading during rep (in lbs)
                 Recorded continuously during IN_REP state
                 
  duration:      Total time from rep start to rep end (in ms)
                 duration = end_time - start_time
                 
  tempo:         Ratio of concentric to eccentric phase durations
                 tempo = concentric_duration / eccentric_duration
                 - tempo > 1.0 = faster concentric (typical for most exercises)
                 - tempo < 1.0 = slower concentric (eccentric emphasis)
                 - tempo ≈ 1.0 = balanced phases
                 
  concentric_duration:  Time from rep start to peak force (lifting phase)
  eccentric_duration:   Time from peak force to rep end (lowering phase)
  
  average_force: Mean force during rep (sum of samples / count)
                 Useful for work calculation
                 
  rom_cm:        Range of motion in centimeters (from IMU position)
                 ROM = max(height) - min(height) during rep

------------------------------------------------------------------------------
19.4 IMU USAGE IN REP DETECTION
------------------------------------------------------------------------------

CURRENT APPROACH (Phase 2):
  IMU is NOT required for basic rep detection. Force threshold crossing is
  sufficient for counting reps. This simplifies implementation and reduces
  algorithm complexity.

IMU DATA ENHANCEMENT (Optional):
  The IMU can enhance rep detection in these ways:
  
  1. PHASE DETECTION:
     - Concentric phase: velocity > 0 (moving up) 
     - Eccentric phase: velocity < 0 (moving down)
     - Peak force typically occurs at phase transition
     
  2. FORM VALIDATION:
     - Excessive acceleration may indicate jerky movement
     - Consistent velocity profiles indicate controlled reps
     
  3. FALSE POSITIVE FILTERING:
     - Force spike WITHOUT corresponding movement = machine jostle
     - Require force AND velocity to start rep for higher accuracy
     
  4. EXERCISE CLASSIFICATION (Future):
     - Different exercises have characteristic motion patterns
     - Vertical vs horizontal movement, rotation, etc.

RECOMMENDATION FOR PHASE 2:
  Implement force-only rep detection first. Log IMU data alongside for
  later analysis. Add IMU-based enhancements in Phase 3+ after collecting
  real workout data to validate patterns.

------------------------------------------------------------------------------
19.5 EDGE CASES AND MITIGATIONS
------------------------------------------------------------------------------

EDGE CASE: Very light weights (<5 lbs)
  - May not exceed START_THRESHOLD reliably
  - Mitigation: Allow threshold adjustment via config
  - Future: Auto-calibrate threshold based on first few reps

EDGE CASE: Isometric holds (static force, no movement)
  - Force sustained but no rep completion
  - Mitigation: MAX_REP_DURATION timeout resets state
  - Log as "hold" event, not "rep"

EDGE CASE: Partial reps (don't complete full ROM)
  - Force may not drop below END_THRESHOLD
  - Mitigation: Accept rep if force drops by >50% of peak
  - Or: Use IMU position to detect direction reversal

EDGE CASE: Machine adjustment (selecting weight)
  - Can cause force spikes during pin insertion
  - Mitigation: Require MIN_REP_DURATION
  - Mitigation: SETTLING_TIME after large force changes

EDGE CASE: Cable bounce at rep end
  - Force oscillates around END_THRESHOLD
  - Mitigation: Require force to stay below END_THRESHOLD for debounce period (50ms)

EDGE CASE: Walking away mid-set
  - Device should reset rep state
  - Mitigation: If no force > noise floor for 30 seconds, reset session

20. SENSOR SYNCHRONIZATION & TIMING
================================================================================

This section describes how to maintain temporal alignment between sensors.

------------------------------------------------------------------------------
20.1 CURRENT TIMING ARCHITECTURE
------------------------------------------------------------------------------

The firmware uses a non-blocking loop with millis()-based timing:

  loop() {
    now = millis()
    
    // Load cell: every 200ms (5 Hz)
    if (now - lastLoadCell >= 200) {
      weight = loadcell::read()
      delay(5)  // I2C settling
      lastLoadCell = now
    }
    
    // IMU: every 50ms (20 Hz)
    if (now - lastIMU >= 50) {
      delay(2)  // I2C settling
      imu = imu::read()
      position::update(imu)
      lastIMU = now
    }
    
    // BLE: every 100ms (10 Hz)
    if (now - lastBLE >= 100) {
      ble::send(position, weight)
      lastBLE = now
    }
  }

KEY TIMING CONSTRAINTS:
  - Load cell and IMU cannot read simultaneously (shared I2C bus)
  - Small delays between reads prevent I2C bus contention
  - BLE sends most recent readings from each sensor

------------------------------------------------------------------------------
20.2 SYNCHRONIZATION APPROACH
------------------------------------------------------------------------------

CURRENT STRATEGY: Nearest-Neighbor Interpolation
  - Each BLE packet contains the LATEST reading from each sensor
  - Sensors are read back-to-back in the loop to minimize temporal skew
  - Timestamp reflects BLE transmission time (millis() at send)
  - Client should treat data as "approximately simultaneous"

TEMPORAL SKEW ANALYSIS:
  - Load cell reads every 200ms, IMU every 50ms, BLE every 100ms
  - Maximum skew between load cell and IMU: ~200ms (worst case)
  - Typical skew: <50ms (within one IMU sample period)
  - For rep detection, this is acceptable (rep durations are 500-3000ms)

FUTURE ENHANCEMENT (Phase 3+):
  If tighter synchronization is needed:
  1. Buffer both sensors with timestamps
  2. Interpolate load cell readings to match IMU timestamps
  3. Send synchronized samples at fixed intervals
  
  This adds complexity and memory usage, so defer until proven necessary.

------------------------------------------------------------------------------
20.3 TIMING DIAGRAM
------------------------------------------------------------------------------

Time (ms) -->  0    50   100  150  200  250  300  350  400
              |    |    |    |    |    |    |    |    |
Load Cell     R---------R---------R---------R---------R
              ↓         ↓         ↓         ↓         ↓
              W1        W2        W3        W4        W5
              
IMU           R----R----R----R----R----R----R----R----R
              ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓
              I1   I2   I3   I4   I5   I6   I7   I8   I9
              
BLE TX             X---------X---------X---------X----
                   ↓         ↓         ↓         ↓
                   (I2,W1)   (I4,W2)   (I7,W3)   (I9,W4)

Legend: R = Read, X = Transmit, W = Weight sample, I = IMU sample

BLE packets contain the most recent weight and IMU readings available.

21.3 EXPLICITLY OUT OF SCOPE
------------------------------------------------------------------------------

These features are NOT planned for the foreseeable future:

  - Touchscreen or display on device
  - Audio feedback (beeps, voice)
  - WiFi connectivity (BLE only)
  - GPS or location tracking
  - Heart rate monitoring integration
  - Camera or video capture
  - Direct cloud connectivity (phone app mediates)
